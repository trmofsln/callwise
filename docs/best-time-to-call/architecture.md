# Best Time to Call implementation

The interactive application returns completed-meeting recommendations or explicit insufficient-support states. It does not retrain, make calls, book meetings, or alter production tables. The user's `meeting_done` objective overrides PS03's `meeting_fixed` objective; fixed meetings and connects remain separate diagnostics.

## Data and offline pipeline

Source 13 is the canonical extraction candidate; source 70 retains its original general-query role. `REDDASH_TRAINING_QUERY_ID` owns query 47566 and is separate from both interactive query IDs. Extraction is read-only, capped at 75 hashed IDs in each of four fixed hour buckets across 17 dates. Each checkpoint records query text/hash, extraction time, and rows. Production imposes statement timeouts; an expensive meeting/UCID reconciliation query timed out and was not scaled further.

`ml.prepare` normalizes actual call-start times, checks seller linkage, retains missing enrichments, deduplicates meaningful UCIDs with source-ID fallback, and writes checksummed JSONL plus quality/manifests. Naive timestamps use an explicitly disclosed Asia/Kolkata assumption. Extraction-time availability is a conservative observation bound, **not** proof that an event was available historically. All pilot `history_complete` flags remain false and canonical labels remain null. The supplemental linked-DSR recording proxy is only an observation audit; its zero values must never become completed-meeting negatives.

`ml.asof.build_asof_features` computes counts and retry gaps using prior call times **and** prior availability times. It excludes mutable/unverified metadata and current/future outcomes. Canonical outcome history also requires maturity and reliable label availability before the decision. The history trainer uses time/count/gap features; seller IDs identify partitions and bootstrap clusters, never model inputs.

Original split membership is immutable. `splits-v2.json` corrects an embargo boundary before any fitting or final-test scoring; the original blocked manifest remains available. History partitions retain lead chains; cold-start partitions keep sellers and leads disjoint. The trainers reject missing labels/history, homogeneous labels, horizon overlap, checksum changes, and repeated final-test evaluation. Logistic candidates, observed hour/day shrinkage, feature ablations, validation-only Platt fitting, and seller-cluster uncertainty are implemented. No candidate has actually been trained on this pilot.

## Server and model contract

Portable versioned JSON artifacts avoid a separate Python inference service. The server loads `.data/best-time-to-call/models/history_aware.json` and `cold_start.json`, with mtime caching and a 2 MB limit. It requires the meeting_done target, canonical label provenance, dataset/split hashes, supported feature schemas, reconciled evidence counts, approved deployment metadata and supported calibration. Proxy, missing, malformed, unapproved, or uncalibrated artifacts fail closed. Offline trainers always produce unapproved candidates; final evaluation alone never deploys a model.

Routing distinguishes reliable history, sparse observed history, verified first contact, and failed/missing retrieval. A successful empty source-13 lookup does not establish complete archived first-contact history: current inference sets `first_contact_verified=false`. Sparse history uses the approved cohort path without arbitrary ensemble weights. Canonical model paths remain unavailable. Live recommendations first use conclusive personal slot evidence; inconclusive sellers use the separately verified general ERP model for advisory ranking, including new sellers without observed calls.

`candidateWindows` returns future hourly windows in the configured timezone, skipping business-day/hour exclusions, cooldown violations, known appointments, do-not-call markers, daily/sequence limits, and inconsistent history. Defaults are 10:00–18:00 Monday–Saturday, a 60-minute cooldown, three daily attempts and ten attempts per seven-day sequence. They are conservative application assumptions, **not verified company policy**. No validated employee-capacity/contact-preference feed exists. Historically answered hours also enter the eligible set, even outside configured hours. DSR entry clocks supply explicitly approximate slot evidence and conservative cooldown/attempt accounting when actual starts are absent. Missing call times do not invalidate a successful history fetch. An unknown future appointment time blocks that date, while default appointment times without dates do not block anything. Sequence caps roll forward as calls leave the lookback; lifetime calls are not a retry budget. Recommendations require a successful history and contact-restriction fetch; missing profiles and DNC markers return no calling window.

The live hierarchy ranks personal hours by linked successful ERP meetings when at least two distinct calls have linked successes; otherwise at least three answered calls, including two in one hour, enable answer-count ranking. Deduplication prefers actual outbound C2C starts over DSR entry clocks. Unlinked meetings never choose a slot. Known answered durations below 20 seconds reduce priority by 75% times their fraction among known answered durations; missing duration stays unknown. With inconclusive personal evidence, approved canonical artifacts may supply probabilities, followed by the frozen general ERP proxy model for ordinal suggestions. Sparse weekdays back off to hour-pooled training bins, whose calibration is unverified. The failed-support first-contact experiment is not used as the general fallback. Configured chronological hours are the final fallback when no supported model exists. Personal/proxy ranking keeps canonical scores and uncertainty null; separately named proxy estimates cannot pass the canonical probability guard. At most four alternatives are returned in one overall ranked_windows list, with a per-day cap and recommended_window as the first choice. daily_windows remains a JSON grouping of those selected choices for compatibility; the UI does not reset ranks each day. Observed weekday success/answer evidence identifies the strongest weekdays; explicit preferences take precedence, and other allowed days remain fallback choices. Supported weekday-and-hour counts replace pooled hourly counts; sparse weekdays use pooled-hour fallback. Three actual daily attempts and four overall suggestions are separate limits. Retry candidate delays are enumerated but not claimed to have measured policy yield; defaults merely enforce operating constraints. A confirmed contact ends the prior unanswered sequence. The 15-minute production rule remains unverified.

## LLM review and independent validation

The OpenAI Docs skill informed compatibility checks. The requested model remains `openai/gpt-6-luna` through OpenRouter; the live tool review succeeds with the application's `reasoning: {effort: 'none'}` request. The old key authenticated but exceeded its monthly limit. The user's reference script identified a working key, saved locally without exposure. Actual structured tool review now passes. Admin verification status is tied to the current configuration and expires after 24 hours; failures retain deterministic fallback.

Only compact counts, quality messages, context IDs, constrained windows and tool outputs reach the model. JWTs, OpenRouter keys, names, phones, recording URLs, raw Global Context snapshots and transcripts never enter prompts. Tools are `get_prediction_context`, the one eligible scoring tool, `score_retry_plan`, and `validate_prediction`; no SQL, shell, training, writes or dialler tools exist. Strict context-ID arguments and backend eligibility checks precede execution. Maximum six tool executions, bounded requests, one repair, 900 output tokens per request, per-seller deadlines and a 20-second batch explanation deadline prevent unbounded loops.

Explanations use an exact factual two-sentence template in the structured-output schema. The LLM reviews that template and numerical evidence instead of adding unrestricted claims. This trades stylistic freedom for testable grounding. Its structured review must match tool/model/version, routing reason, actual windows/scores/timezone, validation status/issues and the template. A separate validator reconstructs the recommendation from the real context and artifacts. It does not certify a future meeting outcome. HTTP errors, invalid tools/arguments, fabricated scores, unavailable artifacts and provider failures preserve deterministic recommendations with explicit fallback status.

## APIs, storage, UI

- `POST /api/users`: existing workflow plus predictions in the response and saved/downloaded JSON.
- `POST /api/predictions`: same validated comma-separated GLIDs, batch recommendation contract.
- `GET /api/predictions/health`: service health separate from model readiness.

- Authenticated `GET /api/admin/experiments`: sanitized extraction and held-out evidence plus a numerical demonstration of the frozen proxy clock models. This route verifies model hashes and cannot promote an artifact.

SQLite adds migrations, prediction settings, call_predictions, model metadata and experiment summaries. Existing admin hashes/sessions, encrypted shared credentials and Global Context snapshots remain intact. Raw datasets/checkpoints/artifacts and lookup exports remain ignored under `.data/`; only aggregate evidence and untrained model cards are committed. The UI shows one overall list of up to four ranked day-and-time choices and shows linked-meeting/answered/short-call evidence, route/support, retry/stop conditions, timestamps, versions and two-sentence explanations; training diagnostics stay in Admin.

Run locally with Node 24 and Python 3.14. Browser and HTTP smoke tests use an isolated SQLite database and browser profile; the live lookup does not alter the user's saved credentials. Deployment remains local and recommendations remain advisory.

## Separate retry contingency

The best next calling window may already be the next attempt after a recorded unanswered call. The retry card now describes a different, explicit contingency: if the proposed call is unanswered, find a later eligible window. It anchors the minimum gap at the end of the proposed window, includes that hypothetical attempt in daily and rolling sequence limits, then independently ranks eligible retries. This protects the gap even if the call is placed late within its suggested hour. A call placed at a different time requires recomputation. The UI displays the exact retry date/time, the recommended wait after the initial window ends and the configured minimum wait. next_window, anchor_at, earliest_retry_at, after_minutes and reason are independently recomputed by validation. The latest observed failure is preserved as previous_unanswered_at; it is not confused with the conditional future retry.


## Model and score display

Every new prediction includes independently validated scoring_model metadata: name, kind, actual artifact family/version, training support, target and the selected model's verified held-out metrics when available. The calling plan shows this information before its alternatives, plus a numerical score for every slot. Canonical probabilities, general ERP proxy estimates and historical ranking points have separate labels. History heuristics do not inherit ML performance metrics; configured-hour fallbacks have no numerical model score. General model ROC AUC/AUPRC come from its frozen-model-matching test-results.json, not from the individual seller or Luna's review. Model and prediction data remain included in the saved JSON export.
